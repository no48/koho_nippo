# track アプリ 機能追加 設計書（3機能）

作成日: 2026-06-07
対象アプリ: track（運輸会社向け 日報・請求管理 / Next.js + Prisma + PostgreSQL）

## 背景

お客様（運輸会社）から以下の要望が挙がった。

1. ~~5月分が20日〜になっている~~ → **別サービスの件と判明。本アプリではスコープ外**
2. 得意先・発地・着地・着地の住所・品名・数量・給与・運賃・通行料・距離手当・給与形態 を「行で追加」できるようにする（日報のまとめ入力）
3. 得意先が最初から全部出てきてほしい（得意先セレクトの改善）
4. 請求書の作成を締め日を元に行いたい

本設計では **②③④** を対象とする。実装は影響範囲の小さい順 **③ → ④ → ②** で進める。

## 全体方針

- 既存仕様を壊さないことを最優先する（受託運用中アプリ）。
- ②は「1日報 = 配送1件」という現行データ前提（一覧・請求書・給与計算が依存）を維持する **A案（フラット・一括登録）** を採用。「まとめ入力」は入力を効率化する UI であり、保存されるデータは現行と同一（1件＝1配送）。親子構造（B案）は全機能改修が必要でリスクが高く、要望に対して過剰なため不採用。

## ③ 得意先が最初から全部出る（小・UIのみ）

### 目的
得意先選択の部品で、文字を打たなくても全得意先が一覧表示されるようにする。

### 対象
- `src/components/ui/customer-autocomplete.tsx`

### 現状
- フォーカス時は `customers.slice(0, 10)`（先頭10件のみ）を表示。
- 文字入力で名前の部分一致フィルタ → `filtered.slice(0, 10)`。

### 変更
- フォーカス時に **全得意先** を表示する（先頭10件制限を撤廃）。
- 文字入力時の絞り込みは維持。ただし結果の `slice(0, 10)` も撤廃し、一致した全件を表示。
- 件数が増えてもUIが崩れないよう、ドロップダウンはスクロール可能にする（`max-h` を現状の `max-h-48` から拡大、例 `max-h-72`）。

### 影響範囲
`CustomerAutocomplete` は「日報フォーム」「請求書作成」「②まとめ入力（新規）」で共通利用されるため、ここの修正で全箇所に反映される。

### 確認観点
- 得意先が0件・1件・多数（数十件以上）でドロップダウンが正しく表示・スクロールできる。
- 既存の選択（onSelect で id/name を返す）挙動が変わっていない。

## ④ 請求書を締め日ベースで作成（中）

### 目的
得意先ごとに設定された締め日（`Customer.closingDay`）を元に、対象月の請求対象期間を自動算出し、その期間の未請求日報を自動収集して請求書を作成できるようにする。

### 締め日 → 期間の計算ルール

新規ユーティリティ `src/lib/billing-period.ts` に `getCustomerBillingPeriod(closingDay, yearMonth)` を実装する。

- 入力: `closingDay`（"1"〜"31" または "末" または null）、`yearMonth`（"YYYY-MM"）
- ルール:
  - 締め日が数値 D の場合: **「N月分」= 前月(D+1)日 〜 当月D日**
    - 例: 締め日20、2026-05 → 2026/04/21 〜 2026/05/20
  - 締め日が "末" の場合: **「N月分」= 当月1日 〜 当月末日**
    - 例: 2026-05 → 2026/05/01 〜 2026/05/31
  - `closingDay` が null/未設定の場合: 既存の全社25日締め（`getPayrollPeriod` と同じ 前月26日〜当月25日）にフォールバック。
- 月末・短い月の処理: 締め日が当月に存在しない日（例: 締め日31で2月）の場合は **その月の末日に丸める**。`new Date(year, month, 0)` で月末日を取得し、`min(D, 月末日)` を用いる。
- 返り値: `{ startDate: Date, endDate: Date, displayText: string }`（displayText 例: "4/21〜5/20"）

### 未請求日報API の拡張
- `src/app/api/reports/unbilled/route.ts`（GET）に任意クエリ `startDate` / `endDate` を追加。
- 指定があれば `reportDate` を `gte: startDate, lte: endDate` で絞り込む（既存の customerId 必須・未請求条件は維持）。

### 請求書作成画面の変更
- `src/app/(dashboard)/invoices/new/page.tsx`
- 基本情報カードに **「対象月」セレクタ** を追加（年月選択。既定は現在の給与期間月）。
- 得意先選択時に、その得意先の `closingDay` を取得（顧客一覧は既に取得しているか、`/api/customers/[id]` で取得）。
- **得意先 + 対象月** が揃ったら:
  1. `getCustomerBillingPeriod(closingDay, 対象月)` で期間を算出。
  2. `/api/reports/unbilled?customerId=...&startDate=...&endDate=...` を呼び、期間内の未請求日報を取得。
  3. 取得した日報を **自動で全選択** する。
  4. 画面に期間テキスト（例「2026年5月分（4/21〜5/20）」）を表示。
- 既存機能は残す:
  - 日報一覧からの遷移（`reportIds` パラメータ）フロー。
  - 手動明細入力。
  - チェックの手動増減（自動選択後もユーザーが調整可能）。

### 確認観点
- 締め日20 / 末 / 未設定 の3パターンで期間が正しく算出される。
- 締め日31で2月対象 → 2/28（または閏年2/29）に丸められる。
- 自動収集された日報が、別フロー（日報一覧からの遷移）と競合しない。
- 既存の手動明細・手動選択が従来どおり動く。

## ② 日報のまとめ入力 ＋「着地の住所」追加（大・DB変更あり）

### 目的
1日分（同一従業員・同一トラック・同一日付）の複数配送を、表形式で複数行まとめて入力・登録できるようにする。あわせて「着地の住所」項目を新設する。

### DB変更（マイグレーション）
- `prisma/schema.prisma` の `DailyReport` に追加:
  - `destinationAddress String? @map("destination_address")  // 着地の住所`
- 既存データは null のままで問題なし（任意項目）。
- マイグレーション名: 例 `add_destination_address_to_daily_report`。

### 新画面「まとめ入力」
- ルート: `src/app/(dashboard)/reports/batch/page.tsx`
- 入口: 日報一覧（`reports/page.tsx`）に「まとめ入力」ボタンを追加（既存「新規登録」と並べる）。
- レイアウト:
  - **ヘッダー（共通・1回だけ選択）**: 日付 / 従業員 / トラック
  - **明細行テーブル（行ごとに入力）**: 得意先 / 発地 / 着地 / 着地の住所 / 品名 / 数量 / 給与 / 運賃 / 通行料 / 距離手当 / 給与形態
  - 「＋ 行を追加」ボタンで行追加、各行に削除ボタン。
  - 得意先列は `CustomerAutocomplete` を使用（③の改善が効く）。発地・着地は `AutocompleteInput`（過去入力補完）を使用。
  - 「まとめて登録」ボタンで一括保存。

### 給与計算の割り切り（設計判断・承認済み）
- まとめ入力の表では **「給与形態」は選択 / 「給与」は手入力** とする。
- 給与形態×作業内容による自動計算（チェックボックス群）は横長の表に不向きなため、従来の「1件入力」フォーム（`reports/new`）にのみ残す。
- まとめ入力で登録した行は `wageType` を保存するが `workItems` は空（後から1件入力で編集すれば自動計算も利用可能）。

### 一括作成API
- 新規 `src/app/api/reports/batch/route.ts`（POST）。
- リクエスト: 共通項目（reportDate, employeeId, truckId）＋ 行配列（customerId, origin, destination, destinationAddress, productName, quantity, salary, fare, tollFee, distanceAllowance, wageType）。
- 1トランザクション内で行数分の `DailyReport` を作成。`reportNumber`（YYYYMMDD-XXX）は既存POSTと同じ採番ロジックを共通化し、同一日付内で連番が衝突しないよう採番する。
- バリデーション: 各行で必須（customerId, origin, destination）を確認。**完全な空行（全項目未入力）はスキップ**。**一部だけ入力された行で必須が欠けている場合はエラー**として保存を中断し、どの行が不正かを通知する。

### 既存「1件入力」フォームへの着地の住所追加
- `src/components/reports/report-form.tsx`（新規/編集兼用）の配送情報カードに「着地の住所」入力を追加。
- `src/app/api/reports/route.ts`（POST）と `src/app/api/reports/[id]/route.ts`（PUT）で `destinationAddress` を受け取り保存。

### 表示への反映（今回のスコープ外）
- 日報一覧・請求書明細への「着地の住所」「数量」の**表示追加は今回のスコープ外**とする（データとして保持できれば目的を満たすため）。表示が必要になれば別途対応する。

### 確認観点
- まとめ入力で複数行を登録 → 一覧に行数分の日報が、共通の日付・従業員・トラックで表示される。
- `reportNumber` が重複しない（同一日に複数行＋既存日報があっても連番が続く）。
- 「着地の住所」が新規・編集・まとめ入力で保存・再表示される。
- 既存の1件入力・編集・給与自動計算が従来どおり動く。
